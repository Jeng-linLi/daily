# 線段樹合併（Segment Tree Merge）：樹上子樹的相異值統計

`solution.py`（Python 3 標準庫）與 `solution.cpp`（C++17）行為完全一致：
有 stdin 走 IO 模式，沒有 stdin 就跑內置斷言並輸出 `all tests passed`。

---

## 題意

給定一棵有 `n` 個節點的**根樹**（根為 `1`），每個節點 `u` 有一個整數標籤 `c[u]`。

對每個節點 `u`，求其子樹中出現過的**相異**（distinct）標籤數量。

限制：`1 ≤ n ≤ 100000`，`|c[u]| ≤ 10^9`。

## 輸入格式

```
n
c_1 c_2 ... c_n
u_1 v_1
u_2 v_2
...
u_{n-1} v_{n-1}
```

前 `n-1` 條無向邊構成這棵樹（根為 `1`）。

## 輸出格式

輸出 `n` 行，第 `u` 行是節點 `u` 的子樹相異標籤數。

任何結構性錯誤（`n` 越界、標籤超界、邊的端點不在 `1..n`、輸入缺 token、
非整數）輸出 `error`。

## 輸入輸出示例

輸入：

```
5
1 2 1 3 2
1 2
1 3
2 4
2 5
```

輸出：

```
3
2
1
1
1
```

樹的形狀與標籤：

```
        1(1)
       /    \
    2(2)   3(1)
    /   \
 4(3)  5(2)
```

驗算：

- 節點 1：子樹 = `{1,2,1,3,2}`，相異值 `{1,2,3}` → **3**
- 節點 2：子樹 = `{2,3,2}`，相異值 `{2,3}` → **2**
- 節點 3：子樹 = `{1}` → **1**
- 節點 4：子樹 = `{3}` → **1**
- 節點 5：子樹 = `{2}` → **1**

## 思路

### 1. 為什麼不能用樸素做法

最直接的想法是「對每個節點都遍歷一次子樹，把標籤塞進 `set`」。
但一個鏈狀樹上，子樹大小總和是 `O(n²)`，直接超時。

改進一點：把小集合併進大集合（启发式合并 / small-to-large），
可以做到 `O(n log² n)`，但仍然要維護 hash 集合，常數不小。

### 2. 線段樹合併的核心想法

換一個視角：**自底向上，把子樹的資訊「合併」到父節點**。

對每個節點 `u` 維護一棵「值域線段樹」，代表 `u` 子樹裡出現過的所有標籤：

| 節點 | 意義 |
|---|---|
| 葉子（某個具體標籤值） | 該標籤是否出現（0 / 1） |
| 內部節點 | 左右兩邊的出現數之和 |

於是 `u` 子樹的相異標籤數 = `u` 那棵線段樹的根節點的 `cnt`。

合併兩棵線段樹 `merge(a, b)` 的規則非常簡單：

```
若 a 為空 → 直接回傳 b
若 b 為空 → 直接回傳 a
否則（兩者都非空，這是唯一需要遞迴的情形）：
    a 的左子樹 = merge(a.left, b.left)
    a 的右子樹 = merge(a.right, b.right)
    a.cnt = a.left.cnt + a.right.cnt
```

底層標籤是「出現／不出現」，所以**葉子合併時取 or（1）而不是相加** ——
這正是「相異」的語意。

### 3. 為什麼總複雜度是 `O(n log V)` 而不是 `O(n²)`

`merge` 裡唯一會「消滅」節點的情形是「a、b 都非空」；
此時 `b` 的根節點被丟棄（不再被任何線段樹引用）。

每次 merge 的「有消耗」呼叫都會消滅一個節點，
而全程建立的節點總數不超過 `O(n log V)`（每個節點插入一個標籤，
最多開 `log V` 個節點）。

所以所有 merge 呼叫加總是 `O(節點總數) = O(n log V)`。
這是線段樹合併最漂亮的地方：**它不需要任何平衡技巧**。

### 4. 實作順序（後序遍歷）

用顯式堆疊做 DFS 取得「父在子前」的順序，再倒過來就是「子在父前」。
對每個節點 `u`（依此順序）：

1. 把 `u` 自己的標籤插入 `root[u]`（此時 `root[u]` 已含所有子樹的貢獻）；
2. `ans[u] = cnt[root[u]]`；
3. 把 `root[u]` 合併進 `root[parent[u]]`。

> ⚠️ `ans[u]` 必須在「合併進父親」**之前**記錄，
> 因為合併會改寫（甚至換掉）那些節點。

### 5. 實作要點

- **值域離散化**：標籤可以到 `±10^9`，先排序去重壓成 `1..V`；
- **用平行陣列存節點**（`left[]` / `right[]` / `cnt[]`）而不是類別物件，
  Python 才不會因為幾百萬個小物件而爆記憶體；
- **節點 0 代表空樹**（`cnt` 恆為 0），省掉大量 `if node is None` 判斷。

## 複雜度

| 項目 | 複雜度 |
|---|---|
| 標籤離散化 | 時間 `O(n log n)` |
| 建立 + 插入 | 時間 `O(n log V)` |
| 所有 merge 合計（節點消耗 amortize） | 時間 `O(n log V)` |
| 總計 | 時間 `O(n log n)` |
| 空間 | `O(n log V)` |

`V` 為不同標籤的個數（`V ≤ n`）。

## 驗證方式

- **固定用例**：單節點、鏈狀樹（標籤全異 / 全同）、星狀樹、
  雙分支樹、負數與 0 標籤、單一標籤的鏈、完全平衡二叉樹 —— 共 8 組；
- **應用程式示範**：`demo_resource_pool_merge()` 用同一套 merge 機制
  實作「資源池合併」並驗證聯集大小；
- **隨機對拍**：200 組小值域（大量重複標籤，壓到「葉子合併」分支）
  + 150 組大值域（幾乎無重複，壓到「內部節點合併」分支）
  + 150 組打亂邊順序的隨機樹
  + 1 組 400 節點深鏈，與「對每個節點遍歷子樹去重」的參考實作比對；
- **Python ↔ C++ 對拍**：stdin/stdout 逐位元組一致。

> 教訓：樸素參考實作一開始寫成「從每個節點出發遍歷**整張圖**」，
> 結果把兄弟子樹也算進去了，與主程式的「子樹」語意不符。
> **對拍的參考實作必須和主程式有完全相同的語意定義。**

## 應用場景（Applications）

- **專案成員技能盤點**：每個節點是一個人，子樹是團隊，
  「團隊涵蓋了幾種技能」就是子樹的相異值數；
- **物種普查**：把觀測點依地理層級組成樹，
  每個區域的物種豐富度（species richness）就是這個問題；
- **授權 / 權限盤點**：群組樹上的「有效權限種類數」；
- **程式碼重複偵測**：以 AST 節點組成樹，統計子樹內的相異節點型別數；
- **依賴分析**：套件依賴樹上，每個子樹用到的相異第三方套件數。
